# Параметризовані сценарії для двох ESP32-S3

Це основа майбутнього конструктора на сайті. Сайт передає **дані сценарію**,
а не скетч C++: прошивка перевіряє кроки, зберігає їх у RAM і виконує через
`millis()`. Після натискання Start сторінку можна закрити: головна ESP32-S3
продовжить сценарій і передаватиме другій каретці команди через ESP-NOW.
Після перезавантаження головної плати сценарій треба завантажити знову.

## Де змінювати код

- `functions/motor_actions.h`: `moveMotorTo(c, meters, speed)`,
  `moveMotorFor(c, direction, speed, durationMs, now)`, `stopMotor(c)`.
- `functions/servo_sequencer.h`: неблокувальний рух і витримки сервоприводу.
- `programs/servo_programs.h`: `moveServoTo`, `holdServoAt`, цикл 0°↔45/90°.
- `functions/light_actions.h`: `setLightMode(c, mode)` — Auto, Off, Red,
  Green, BlinkRed. Auto зберігає стару поведінку: зелений у спокої,
  червоний строб під час руху.
- `programs/scenario_engine.h`: послідовності двох кареток, очікування кроків
  і подій, тайм-аути та аварійне завершення сценарію.
- `programs/scenario_codec.h`: перетворення JSON у перевірені параметри.
- `firmware_impl.h`: Wi-Fi, ESP-NOW, WebSocket та виклик `scenario.tick()`.

Ця структура однакова в Arduino IDE для власної мережі та Home/OTA.
PlatformIO компілює ті самі файли, тому окремої копії сценарної логіки там немає.

## Формат, який зможе надсилати конструктор

`lanes[0]` — кроки каретки 1, `lanes[1]` — кроки каретки 2. Кожна виконує
свою послідовність незалежно. Максимум — 16 кроків на каретку.

```json
{
  "type": "scenario_load",
  "id": 101,
  "lanes": [
    [
      {"action":"move_to","meters":-2.0,"speed":50},
      {"action":"servo_cycle_start","angle":90,"durationMs":1000,"closedHoldMs":2000},
      {"action":"wait_peer","peer":2,"peerCompleted":2,"timeoutMs":30000},
      {"action":"servo_off"},
      {"action":"light","mode":"auto"}
    ],
    [
      {"action":"wait_ms","durationMs":500},
      {"action":"move_to","meters":1.5,"speed":40},
      {"action":"light","mode":"blink_red"},
      {"action":"stop_motor"}
    ]
  ]
}
```

Після відповіді `{"type":"scenario_result","operation":"load", "accepted":true}`
надішліть `{"type":"scenario_start","id":101}`. Ідентифікатор захищає від
випадкового запуску раніше завантаженого плану. Для зупинки —
`{"type":"scenario_stop"}`. У звичайному повідомленні `state` є об'єкт
`scenario` з `id`, `state`, `error`, `completed` і `total` для двох кареток.
Так майбутній інтерфейс зможе підсвічувати активні кроки. Звичайні кнопки
ручного керування зупиняють запущений сценарій.

Доступні дії: `move_to` (метри від встановленого центра), `move_for`
(напрямок `-1`/`1`, швидкість і `durationMs`), `stop_motor`, `servo`
(фізичний кут 0–90° і витримка `durationMs` **після оціненого повороту**),
`servo_cycle_start` (повторювати відкриття/закриття з окремими витримками),
`servo_off`, `light`, `wait_ms`, `wait_peer`, `wait_event`, `emit_event`.
Для зовнішнього датчика зарезервовано `eventId` 1–63. Зараз подію можна
перевірити командою `{"type":"scenario_event","id":101,"eventId":7}`; надалі
обробник реального датчика викличе `scenario.signalEvent(7)`.

`wait_peer` очікує, поки інша каретка завершить указані кроки; `peer` — 1
або 2, `peerCompleted` — кількість завершених кроків. Очікування має
`timeoutMs`, щоб взаємне очікування не тривало безкінечно. Дії руху,
сервоприводу й очікування теж мають тайм-аути; їх можна задати для кожного
кроку окремо. При втраті другої каретки сценарій зупиняє обидва мотори.
Для `move_for` мінімум 200 мс: коротша команда може закінчитися раніше, ніж
друга плата встигне підтвердити рух. Завершення кроків другої каретки
потребує її статусу про застосовану команду; це **не вимір фактичної
координати**.

## Межі поточної реалізації

Сценарій **виконує головна ESP32-S3**. Друга плата зараз отримує поточний
PWM, кут і режим LED та підтверджує застосовані значення. Втрата браузера
не перериває роботу, але втрата головної плати зупиняє другу за тайм-аутом.
Щоб кожен вузол самостійно продовжував програму після втрати головної плати,
потрібна наступна версія протоколу: доставка плану на кожен вузол, перевірка
версії й хешу, підтвердження кожного фрагмента, локальне виконання, обмін
подіями та окремі правила поведінки при втраті зв'язку.

Поточні координати кареток — **оцінка за часом**, а не покази енкодера.
Програма не може гарантувати фактичну відстань між двома каретками на одному
тросі. Перш ніж запускати спільний рух, потрібні вимірювання швидкості в
обидва боки, фізичні упори й перевірка на обладнанні; для надійного
уникнення зіткнення потрібен датчик положення або відстані.

ESP-NOW у ESP32-S3 підтримує максимум 20 записаних peers на один вузол.
Тому схема, де одна ESP напряму підтримує зв'язок із 40 платами, потребує
іншої топології (групи, шлюзи або інший транспорт). Поточний протокол має
версію 2 через нове поле LED: **обидві ESP32-S3 треба прошити версією 2**,
інакше вони не з'єднаються.

Джерело обмеження peers і вимоги підтвердження на рівні застосунку:
[офіційна документація Espressif для ESP32-S3](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/network/esp_now.html).
